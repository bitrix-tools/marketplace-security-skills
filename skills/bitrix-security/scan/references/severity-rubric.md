# Severity Rubric for Bitrix PHP Modules

Единственный источник истины для назначения severity. Назначай ровно один из трёх уровней — `high`, `medium`, `low` — по принципу ниже. При расхождении с точечными подсказками в `vulnerability-checklist.md` (в частности, reflected XSS и Open Redirect) — следуй этой рубрике.

> Этот файл задуман как easily-editable: правь списки ниже, чтобы менять калибровку. SKILL.md и vulnerability-checklist.md ссылаются сюда и не дублируют содержимое.

## HIGH — блокирующий
- неаутентифицированный RCE / Command Injection (eval, system, exec, proc_open, shell_exec, passthru, backtick, addAgent);
- неаутентифицированный Path Traversal / LFI / RFI;
- PHP Object Injection — подтверждённый unserialize без проверки CheckSerializedData / опции allowed_classes;
- неаутентифицированная загрузка произвольных/исполняемых файлов в web-доступную область;
- неаутентифицированный SSRF с доступом к internal-сети и возвратом ответа атакующему или цепочкой к RCE;
- неаутентифицированный XXE — обработка XML с включённой опцией LIBXML_NOENT;
- логирование чувствительных данных в document_root по предсказуемому пути;
- захардкоженные секреты, общие для всех инсталляций модуля (ключи платёжных систем, приватные ключи, мастер-пароли);
- IDOR / mass assignment без проверки владельца, выполняющий привилегированное или денежное действие, доступный анониму или пользователю сайта;
- бизнес-логика с прямым финансовым ущербом без авторизации — манипуляция ценой/количеством/скидкой в корзине, обход купонов, начисление бонусов (sink'и Sale\Order, CSaleBasket, обработчики OnSalePayment/OnSaleOrderSaved);
- подтверждённый бэкдор: обфускация (`eval(gzuncompress(base64_decode(...)))` и подобное), где декодированная логика доводит внешний ввод (запрос, cookie, ответ стороннего хоста) до exec-/файлового sink или отправляет секреты/данные пользователей наружу. Обфускация сама по себе (минификация, упакованные вендорные библиотеки, лицензионные загрузчики, base64-ресурсы, вызовы лицензионного API вендора) — не находка; не присваивай ей тип `RCE`/`Command Injection` без доказанного пути.

## MEDIUM — существенный, не блокирующий
- SQL-инъекция;
- межпривилегиальный stored XSS — данные, внедряемые менее привилегированным атакующим (аноним, клиент, оператор), исполняются в интерфейсе администратора (списки заказов, очереди модерации);
- CSRF на значимое state-changing действие;
- reflected XSS.

А также находки, требующие аутентификации (оператор модуля или администратор) либо специфических условий, которые атакующий не контролирует напрямую:
- эскалация привилегий внутри аутентифицированной зоны (оператор получает действия полного администратора);
- SSRF ограниченного воздействия — исходящие запросы без возврата ответа (blind, egress-only);
- authenticated IDOR, Open Redirect при наличии сессии;
- слабая криптография для security-токенов (mt_rand/rand для сброса пароля и токенов, md5/sha1 без соли для паролей);
- race condition / TOCTOU в чувствительной операции (повторное применение купона, двойное начисление бонуса), если требует аутентификации.

## LOW — hardening / информационный
- Information Disclosure без пользовательских/платёжных данных (версии, пути, debug-вывод);
- CSRF в незначительном действии;
- мёртвый/недостижимый код с опасным паттерном;
- self-XSS (контекст виден только самому пользователю);
- слабая криптография в некритичном для безопасности контексте;
- Open redirect; использование функции `LocalRedirect` — не баг.

## Гейт перед назначением HIGH

HIGH допустим только если атакующий — аноним или обычный пользователь сайта (покупатель,
посетитель, гость с sessid). Если для эксплуатации нужен администратор, право `edit_php`,
право записи в модуль (`W`), доступ в админку или выданный администратором токен/ключ —
это **не HIGH** (см. ниже «Не находка»; в остальных случаях — максимум MEDIUM). Гипотетический
вектор «значение попадёт в БД через стороннюю SQLi / скомпрометированную учётку / любую другую
уязвимость» **не является** путём эксплуатации и не поднимает severity.

## Не находка (не включай в `vulnerabilities`, при желании упомяни в `summary`)
- штатная возможность привилегированной роли: поля, которые **по назначению** содержат код —
  PHP-шаблоны, PHP-условия, режим eval, сырой HTML/JS (счётчики, аналитика), — если их сохраняет
  **только** администратор / пользователь с `edit_php` / правом записи в модуль. (Если же в
  eval/shell/SQL попадает поле, не предназначенное для кода — число, путь, формат, — это
  инъекция, MEDIUM);
- функции удалённого управления, которые являются назначением модуля и доступны только по
  выданному администратором секрету с явным per-token разрешением (выдача токена = решение
  администратора). Находкой становится обход проверки токена, слабое/небезопасное сравнение,
  разрешение по умолчанию без явного выбора администратора или утечка токена;
- обфускация / упакованные лицензионные загрузчики, если декодированная логика не доводит
  **внешний ввод** до опасного sink. Обращение к лицензионному API вендора по фиксированному
  адресу — не «сетевой sink с эксфильтрацией»;
- публичные (не секретные) значения: публичный хеш-ключ лицензии Bitrix
  (`getPublicHashKey()`) и производные от него метки на страницах; опубликованные платёжной
  системой тестовые/sandbox-реквизиты в подсказках, lang-файлах и описаниях;
- данные или действия, которые по модели доступа модуля и так разрешены этой роли (общедоступный
  для всех авторизованных/сотрудников справочник, публичный счётчик лайков/просмотров, выдача
  купона анониму как задуманная механика с серверными ограничениями);
- серверный метод, принимающий ID, если не доказано, что ID приходит из достижимого
  клиентского entry point (а не из настроек, подписанного payload или серверного кода);
- поведение, повторяющее штатный компонент ядра (например, привязка гостевого заказа к
  существующему пользователю по e-mail/телефону, как `ALLOW_APPEND_ORDER` в
  `bitrix:sale.order.ajax`), если модуль не даёт атакующему сверх этого доступ к чужим данным;
- анонимный action с доказанной компенсирующей проверкой (подпись `hash_equals`, проверка
  владельца/администратора): «отклонение от безопасного дефолта» само по себе не находка.

## Частые пересечения границ
- клиент выбирает один из **валидных серверных** вариантов цены/тарифа (а не задаёт сумму):
  не HIGH; MEDIUM только при доказанной финансовой выгоде, иначе LOW;
- обнуление/пропуск стоимости доставки при некорректном варианте: MEDIUM, не HIGH (HIGH остаётся
  за прямой манипуляцией ценой/количеством/скидкой товаров и оплатой);
- отладочное логирование секретов, включаемое только скрытой опцией, выключенной по умолчанию и
  недоступной в интерфейсе: LOW. HIGH «логирование в document_root» — только если запись идёт в
  штатном режиме и трассировка доказывает, что секрет **реально попадает** в записываемые данные;
- отключённая проверка TLS при запросе к фиксированному адресу вендора без секретов в канале: LOW;
- автономные скрипты восстановления/развёртывания, которые по своей природе работают без ядра
  Bitrix и выкладываются администратором вручную на время операции (как штатный `restore.php`):
  не HIGH; максимум LOW с рекомендацией одноразового секрета и самоудаления.

`riskLevel` = максимальная severity среди всех находок. `none` если уязвимостей нет.
